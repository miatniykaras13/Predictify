

**Predictify** — веб-платформа для прогнозирования исходов событий и соревнования в рейтинге участников. Пользователь выбирает один из предложенных исходов и получает виртуальные очки за верный прогноз. Количество очков зависит от коэффициента, рассчитанного по распределению прогнозов участников.

Проект вдохновлён Polymarket. Денежные ставки, платежи и вывод средств отсутствуют. Создание прогноза не расходует виртуальные очки, а неверный прогноз не уменьшает накопленный баланс.

### Изображения и аватарки

Аватарка профиля и изображение события необязательны. Файлы хранятся в MinIO, а их ключи — в полях `users.avatar_key` и `events.image_key` типа `varchar(255)`, допускающих `NULL`. Каждому пользователю соответствует не более одной аватарки, каждому событию — не более одного изображения.

Backend формирует URL для отображения файлов; временные ссылки MinIO в базе данных не сохраняются. При удалении аватарки или изображения соответствующее поле получает значение `NULL`, а интерфейс показывает стандартную иконку или заглушку. Сервер проверяет формат и размер загружаемых файлов.

### Правила коэффициентов и начисления очков

Коэффициент исхода:
K = N / n, но не больше 10
(N — всего прогнозов, n — прогнозов на этот исход)
Округляем до 2 знаков (0,005 и выше — вверх).

Очки:
Угадал → 100 × K
Не угадал → 0

Крайние случаи:
· Пока никто не голосовал (N = 0) → K = число вариантов (но не больше 10)
· На исход никто не поставил (n = 0) → K = 10

Пример: 10 человек, 8 за A, 2 за B → K(A) = 1,25; K(B) = 5,00. Если верно B — каждый получит 100 × 5 = 500 очков.

Отмена ошибочного начисления при исправлении результата относится только к соответствующему событию. Дополнительный штраф за неверный прогноз не применяется, произвольное изменение общего баланса запрещено.

### Жизненный цикл события

```mermaid
stateDiagram-v2
    state "Открыто" as Open
    state "Рассчитывается" as Calculating
    state "Завершено" as Completed
    state "Отменено" as Cancelled

    [*] --> Open: Публикация
    Open --> Calculating: Срок или досрочное закрытие
    Calculating --> Completed: Все начисления выполнены
    Open --> Cancelled: Отмена с причиной
    Completed --> Calculating: Исправление исхода администратором
```

В момент сохранения прогноза серверное время должно быть строго меньше срока закрытия. Перенос ожидаемой даты результата не возобновляет приём прогнозов и не меняет зафиксированные коэффициенты. При задержке результата событие остаётся в ожидании; автоматический выбор исхода не выполняется.

## Запуск через Docker Compose

Из корня репозитория скопируйте пример окружения в рабочий `.env`.

```sh
cp .env.example .env
```

Заполните `POSTGRES_PASSWORD` и `MINIO_ROOT_PASSWORD` разными значениями. Для каждого пароля можно выполнить `openssl rand -hex 24`. Используйте в пароле PostgreSQL только URL-безопасные символы, поскольку пароль входит в строку подключения backend. Порты на `127.0.0.1` можно переопределить в `.env`.

Режим разработки использует `compose.override.yml` автоматически. Правки в каталогах `src` frontend и backend подхватываются при работающих контейнерах. После изменений зависимостей или конфигурации повторите команду с `--build`.

```sh
docker compose up -d --build --wait
```

Для проверки собранного приложения укажите только основной файл.

```sh
docker compose -f compose.yml up -d --build --wait
```

При стандартных портах frontend доступен по адресу `http://127.0.0.1:5173`, консоль MinIO — `http://127.0.0.1:9001`. Проверить готовность API через frontend можно командой `curl -fsS http://127.0.0.1:5173/api/ready`.

Миграции применяются при запуске до старта backend. В режиме разработки их также можно запустить вручную.

```sh
docker compose run --rm migrate
```

Для собранного режима добавьте `-f compose.yml` после `docker compose`. Остановить сервисы с сохранением именованных томов можно через `docker compose down`. При смене режима выполните `down` перед запуском с другим набором файлов.

Если PostgreSQL ранее запускался через Compose из каталога backend, сделайте `pg_dump` и остановите старый контейнер. Запустите только новый PostgreSQL командой `docker compose up -d --wait postgres`, восстановите дамп и затем запустите все сервисы.

## Запуск frontend

Установите Node.js 24 и выполните из корня репозитория.

```sh
npm ci
npm run dev -w frontend
```

Откройте адрес, который выведет Vite. Оболочка и заглушки публичных страниц запускаются без backend. На `/dev/ui` доступны примеры всех общих компонентов и состояний.

```sh
npm run test -w frontend
npm run build -w frontend
npm run preview -w frontend
```

Сборка проверяет типы и записывает результат в `frontend/dist`. Команда `preview` позволяет проверить собранное приложение локально.

### Структура и подключение модулей

- `frontend/src/app` содержит общий layout, навигацию, базовые стили и таблицу маршрутов в `routes.tsx`.

### Общие компоненты

Импортируйте `Button`, `TextField`, `Textarea`, `Modal`, `LoadingState`, `ErrorState` и `EmptyState` из `shared/ui`, используя относительный путь от своего модуля.

```tsx
<>
  <TextField label="Публичное имя" name="displayName" error={nameError} />
  <Button onClick={() => setIsOpen(true)}>Сохранить</Button>
  <Modal title="Подтверждение" open={isOpen} onClose={() => setIsOpen(false)}>
    <p>Сохранить изменения?</p>
    <Button onClick={save}>Подтвердить</Button>
  </Modal>
  <ErrorState description="Сервис временно недоступен." onRetry={reload} />
</>
```

Поля передают стандартные атрибуты элементам формы. `Button` по умолчанию имеет тип `button`. `Modal` управляется через `open` и вызывает `onClose` по кнопке и `Escape`. `LoadingState` сообщает о загрузке, а `EmptyState` показывает пустой результат и при необходимости принимает действие через `action`.

### API и размещение

Импортируйте `apiRequest` и `ApiError` из `shared/api/apiRequest`. Передавайте путь от базы API с начальной `/`, параметры запроса через `URLSearchParams`, данные через `json` или `body`, а сигнал отмены через `signal`.

```ts
const query = new URLSearchParams({ limit: '20' });
const events = await apiRequest<EventSummary[]>(`/events?${query}`, { signal });
```

Это пример вызова для модуля каталога. Ответ с JSON возвращается как тип `T`, заданный вызывающим модулем. Для `204` используйте `apiRequest<void>`. `ApiError.kind` различает `http`, `network` и `invalid-json`. Для HTTP-ошибок доступны `status` и `details`. Отмена запроса передаётся вызывающему коду в исходном виде.

По умолчанию клиент обращается к `/api` на том же адресе, что и приложение. Скопируйте `frontend/.env.example` в `frontend/.env.local`, если нужно задать `API_PROXY_TARGET` для локального backend. Vite проксирует `/api` с сохранением префикса. `VITE_API_BASE_URL` при необходимости переопределяет базу при сборке. Эта переменная публичная.

В Compose `vite dev` и `vite preview` проксируют `/api` и `/api/*` в backend. Режим `preview` раздаёт `frontend/dist` и поддерживает прямые переходы по маршрутам приложения, например `/leaderboard`. Учётные данные и формат доменных ответов определяют соответствующие модули.

## Проверки качества

Для локального запуска установите Node.js 24 и выполните команды из корня репозитория.

```sh
npm ci
npm run lint
npm run format:check
```

ESLint проверяет код в `frontend/` и `backend/`. Prettier проверяет форматирование файлов приложений и конфигурации инструментов. Чтобы применить форматирование, выполните `npm run format`.

Пишите сообщения коммитов по [Conventional Commits](https://www.conventionalcommits.org/), например `feat(frontend): add event filters` или `fix(backend): validate event deadline`.

Перед открытием PR в `develop` проверьте сообщения коммитов локально.

```sh
git fetch origin
npm run commitlint -- --from origin/develop --to HEAD
```

Для PR в `main` используйте `origin/main` вместо `origin/develop`. GitHub Actions запускает линтинг, проверку форматирования и проверку сообщений коммитов для обеих целевых веток.

Ветки `features/*` вливаются в `develop`, а `develop` в `main` через **Create a merge commit**. Commitlint проверяет обычные коммиты, которые PR добавляет в целевую ветку. Git исключает служебные merge-коммиты по числу родителей.
