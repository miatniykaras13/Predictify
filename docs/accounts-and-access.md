# Модель аккаунтов и правила доступа

Контракт для [#6](https://github.com/miatniykaras13/Predictify/issues/6) (аккаунты и сессии), [#7](https://github.com/miatniykaras13/Predictify/issues/7) (профиль и восстановление) и [#8](https://github.com/miatniykaras13/Predictify/issues/8) (полномочия). Основание — [ТЗ](../README.md#функциональные-требования), FR-01, FR-02, FR-05, FR-19 и FR-20. Модули событий, прогнозов и результатов используют описанный здесь серверный интерфейс доступа.

## Модель данных

| Таблица в схеме `app` | Данные и ограничения |
| --- | --- |
| `users` | `id bigint` — первичный ключ. `email` — уникальный нормализованный адрес (удалить пробелы по краям и привести к нижнему регистру). `public_name`, `password_hash`, `role` обязательны. Допустимы роли `user`, `moderator` и `admin`. `avatar_key varchar(255)` допускает `NULL`. |
| `sessions` | `id uuid` — первичный ключ, `user_id bigint` — внешний ключ на `users`. Хранит уникальный `refresh_token_hash`, `expires_at` и `revoked_at` (`NULL` до отзыва). У пользователя может быть несколько сессий. |
| `password_reset_tokens` | `token_hash` — первичный ключ, `user_id bigint` — внешний ключ на `users`. Хранит `expires_at` и `used_at` (`NULL` до использования). Действительность токена проверяется и обновляется атомарно при сбросе пароля. |
| `moderator_category_assignments` | Составной первичный ключ (`user_id`, `category_id`) и внешние ключи на пользователя и категорию. Пользователь с ролью `moderator` может иметь несколько категорий, а категория — несколько модераторов. |

Гость — состояние запроса без сессии. Регистрация создаёт только роль `user`. Начальные очки равны `0`, пока в журнале начислений нет записей для пользователя. Баланс читает модуль начислений, он рассчитывается по журналу. В JSON идентификаторы из PostgreSQL `bigint` передаются десятичными строками. Поля времени хранятся как `timestamptz`. Пароли хранятся как адаптивные хеши с солью. Исходные токены восстановления и обновления передаются только при выдаче и использовании.

В MinIO хранится текущий файл. `users.avatar_key` хранит ключ объекта. Backend формирует доступный браузеру `avatarUrl` при выдаче профиля через общий `getAvatarUrl(user)`. При `NULL` API возвращает `avatarUrl: null`, а клиент показывает стандартную иконку. Временный URL в БД не записывается.

## HTTP API

Ошибка в JSON имеет вид `{ "error": "CODE", "message": "Сообщение" }`. `400` означает некорректные данные, `401` — отсутствующую, недействительную или завершённую сессию (либо неверные данные входа), `403` — нехватку прав при действительной сессии или недопустимый Origin, `404` — отсутствующий ресурс или скрытый от запрашивающего черновик, `409` — дубликат или конфликт состояния. Ответы с токеном и личными данными используют `Cache-Control: no-store`.

### Аккаунт и сессия

| Метод и путь | Вход | Ответ |
| --- | --- | --- |
| `POST /api/auth/register` | `{ email, password, publicName }` | `201` с `{ id, publicName }`. После регистрации вход выполняется отдельным запросом. `400` для лишних полей, включая `role` и `balance`, `409` для занятой почты. |
| `POST /api/auth/login` | `{ email, password }` | `200` с `{ accessToken, expiresIn }` и кукой обновления. `401` с одинаковым ответом для неизвестной почты и неверного пароля. |
| `POST /api/auth/refresh` | Кука обновления | `200` с `{ accessToken, expiresIn }` и новой кукой. `401` для отсутствующего, просроченного, заменённого или отозванного токена. |
| `POST /api/auth/logout` | Кука обновления | `204`. Отзывает сессию, соответствующую действующему refresh token, и очищает куку. Клиент дожидается текущего обновления токена перед выходом и прекращает новые попытки обновления. При уже завершённой или отсутствующей сессии возвращает тот же ответ. |
| `POST /api/auth/password-reset/request` | `{ email }` | `202` для любого синтаксически корректного адреса. Для существующего аккаунта отправляет ссылку с одноразовым токеном на почту. |
| `POST /api/auth/password-reset/confirm` | `{ token, newPassword }` | `204` после смены пароля. `400 INVALID_RESET_TOKEN` для неизвестного, истёкшего или использованного токена. |

Access token подписан, действует до 15 минут в пределах срока сессии и содержит `sub` (ID пользователя) и `sid` (ID сессии). `expiresIn` указывается в секундах. Frontend хранит access token в памяти и отправляет в `Authorization: Bearer <token>`. Защищённый запрос проверяет подпись, срок действия и соответствие `sub` активной сессии `sid` в БД. Refresh token — случайное непрозрачное значение в куке `HttpOnly; SameSite=Lax; Path=/api/auth` с `Secure` при HTTPS. Для входа, обновления и выхода backend проверяет `Origin` по настроенному origin приложения.

Сессия длится 7 суток с входа. Обновление атомарно заменяет хеш refresh token в действующей сессии, сохраняя исходный срок сессии. Только один из одновременных запросов с одним токеном получает новую пару. Проигравший запрос оставляет куку без изменений. Клиент объединяет параллельные попытки обновления в один запрос. Выход делает уже выданный access token этой сессии недействительным при следующей проверке.

Токен восстановления действует 30 минут. Успешная смена или сброс пароля одной транзакцией меняет хеш, отзывает все сессии пользователя и делает недействительными все оставшиеся токены восстановления. Обновление сессии и выдача сессии при входе проверяют актуальное состояние аккаунта с учётом этой транзакции. При восстановлении адрес и токен исключаются из журналов запросов.

### Личный кабинет

Все маршруты используют пользователя из сессии.

| Метод и путь | Вход | Ответ |
| --- | --- | --- |
| `GET /api/me` | — | `200` с `{ id, publicName, email, avatarUrl, role, categoryIds }`. `categoryIds` содержит текущие назначения, включая архивные, для модератора. У остальных ролей — пустой список. |
| `PATCH /api/me` | `{ publicName }` | `200` с обновлённым профилем в формате `GET /api/me`. |
| `PUT /api/me/password` | `{ currentPassword, newPassword }` | `204`, после чего нужно войти заново. `400 INVALID_CURRENT_PASSWORD` при неверном текущем пароле. |
| `PUT /api/me/avatar` | `multipart/form-data`, один файл в поле `avatar` | `200` с `{ avatarUrl }`. Поддерживаются JPEG, PNG и WebP до 2 МиБ с проверкой содержимого на сервере. `413` для превышения размера, `415` для неподдерживаемого формата. |
| `DELETE /api/me/avatar` | — | `204`, в том числе при отсутствии файла. `avatar_key` становится `NULL`. |
| `GET /api/me/balance`, `GET /api/me/predictions` | — | Баланс и история в контракте модуля [#22](https://github.com/miatniykaras13/Predictify/issues/22). |

Для каждой загрузки backend создаёт новый ключ. После загрузки он получает предыдущий ключ и обновляет профиль под одной блокировкой записи пользователя. Очистка предыдущего объекта выполняется после фиксации изменения. Если запись не удалась, backend удаляет загруженный объект и сохраняет текущую аватарку. Публичные ответы и панель управления модераторами используют отдельные модели ответа. Почта и история прогнозов доступны только через личные маршруты владельца. API исключает пароли, хеши, служебные токены и ключи хранилища из ответов.

### Назначения модераторов

Доступно администратору. Маршруты используются панелью управления модераторами.

| Метод и путь | Вход | Ответ |
| --- | --- | --- |
| `GET /api/admin/moderators` | Необязательные `query` (ID или часть публичного имени), `role` (`user` или `moderator`), `limit` (по умолчанию 20, максимум 100), `offset` (по умолчанию 0) | `200` с `{ items: [{ id, publicName, role, categoryIds }] }`. Включает текущих модераторов и кандидатов, сортирует по `id`. |
| `PUT /api/admin/moderators/{userId}` | `{ categoryIds, reason }`, непустой список уникальных ID существующих категорий и непустая причина | `200` с `{ id, role, categoryIds }`. Назначает роль `moderator` и заменяет список категорий целиком. `400` для недопустимого списка, `404` для неизвестного пользователя, `409` при попытке изменить роль администратора. |
| `POST /api/admin/moderators/{userId}/revoke` | `{ reason }`, непустая причина | `204`. Удаляет все назначения и возвращает роль `user`. Для обычного пользователя также `204`. `404` для неизвестного пользователя, `409` для администратора. |

Изменения роли и назначений вступают в силу в одной транзакции с записью аудита. Повторный запрос с тем же набором категорий сохраняет состояние без новой записи. Назначение в архивную категорию даёт доступ к разрешённым действиям над ранее опубликованными событиями. При удалении категории модуль категорий в одной транзакции очищает её назначения и записывает изменения в аудит. Модератор, потерявший последнее назначение, получает роль `user`. События, прогнозы и начисленные очки при смене полномочий сохраняются.

## Матрица прав

«Своя категория» — категория, в которую модератор назначен в момент операции. «Свой черновик» — черновик этого автора в его текущей категории. Для операций над событиями также действуют ограничения по состоянию из ТЗ.

| Действие | Гость | Пользователь | Модератор | Администратор |
| --- | --- | --- | --- | --- |
| Публичные категории, события, коэффициенты, результаты и лидерборд | Да | Да | Да | Да |
| Регистрация, вход и восстановление | Да | Да | Да | Да |
| Свой профиль, баланс и история, смена имени, пароля и аватарки, выход | — | Да | Да | Да |
| Создание или замена своего прогноза до закрытия | — | Да | Да | Да |
| Просмотр, редактирование и удаление черновиков | — | — | Свои черновики | Все черновики |
| Создание черновика и публикация | — | — | Свои черновики в активных назначенных категориях | Любые активные категории |
| Допустимые уточнения и изменение изображения опубликованного события | — | — | Свои категории | Все категории |
| Досрочное закрытие, подтверждение исхода и отмена открытого или ожидающего результата события | — | — | Свои категории, включая архивные | Все категории, включая архивные |
| Исправление результата или отмена завершённого события | — | — | — | Да |
| Управление категориями и модераторами | — | — | — | Да |
| Журнал действий | — | — | Действия над событиями в своих категориях | Полный журнал |

## Серверная проверка

Общий интерфейс используют модули событий, прогнозов, результатов, профиля и административных панелей.

| Вызов | Контракт |
| --- | --- |
| `requireSession(request)` | Возвращает `{ userId, sessionId }` из проверенной сессии. При отсутствии действительной сессии возвращает ошибку `401`. |
| `requireOwner(actor, ownerId)` | Сравнивает владельца ресурса с `actor.userId`. Для чужого личного ресурса возвращает `403`. Роль администратора сама по себе не даёт доступа к чужому личному кабинету. |
| `requireAdmin(actor, db)` | Загружает актуальную роль в БД и требует `admin`, иначе `403`. |
| `requireCategoryAccess(actor, categoryId, db)` | Разрешает администратору либо модератору с текущим назначением в категории. Иначе `403`. Модуль события дополнительно проверяет автора черновика, состояние события и допустимость действия в архивной категории. Для доступа к скрытому черновику возвращается `404`. |

Клиент использует роль и категории для отображения интерфейса. Backend определяет ID пользователя из сессии, а ID категории для существующего события — из записи события в БД. Служебные операции проверяют роль и назначения по актуальным данным PostgreSQL. Для записи проверка и действие выполняются в одной транзакции. Проверка блокирует запись пользователя до завершения транзакции. Изменение его роли или назначений использует ту же блокировку. После фиксации отзыва любая следующая проверка отклоняет служебное действие, даже если access token ещё действует. Чтение панелей и журнала фильтрует данные по текущим полномочиям на сервере.

В журнал попадают публикации, закрытия, отмены, подтверждения, исправления, изменения назначений и изображения опубликованных событий. Запись содержит действие, ID исполнителя, время сервера, тип и ID объекта, категорию для действий над событием, причину по правилам операции и изменённые значения «до» и «после». Для системного закрытия исполнитель обозначается как система. Изменения назначений видны администратору. Модератор видит журнал действий над событиями только в категориях, в которые он назначен на момент чтения.

## Сценарии для реализации

| Сценарий | Ожидаемый результат |
| --- | --- |
| Регистрация с полем `role` или с почтой, уже занятой в другом регистре | `400` за лишнее поле, `409` за дубликат. При успешной регистрации роль `user`, баланс `0`. |
| Выход и повторный запрос с прежним access token | `401` для завершённой сессии. Другие сессии пользователя действуют. |
| Два запроса с одним refresh token либо повторный сброс пароля с использованным токеном | Успешен ровно один запрос. После сброса пароля все предшествующие сессии завершены. |
| Попытка прочитать чужую историю, почту или черновик другого модератора | Личные маршруты возвращают только данные владельца сессии. Чужой черновик скрыт в списке, прямой запрос получает `404`. |
| Отзыв категории при активной сессии модератора | Действие над событием этой категории получает `403`, журнал категории скрывается. Свой профиль по-прежнему доступен. Аудит хранит прежние и новые назначения. События, прогнозы и очки сохранены. |
| Попытка начать новое событие либо завершить ранее опубликованное в архивной категории | Создание и публикация отклоняются из-за статуса категории. Модератор с назначением или администратор может закрыть, отменить или подтвердить ранее опубликованное событие при допустимом состоянии. |
| Удаление аватарки и загрузка неподдерживаемого файла | Удаление возвращает профиль к стандартной иконке. Неподдерживаемый файл отклоняется, текущая аватарка сохраняется. |
